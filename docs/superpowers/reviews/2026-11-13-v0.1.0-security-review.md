## Findings

Three real gaps were found by the walk (rows 1, 2, 13) and fixed in `security: mask secret keys in settings form, autoload=false on secrets, validate webhook override`. Nothing is left open as a blocker. Known issues accepted for v0.1.0:

| ID | Severity | Issue | Plan |
|---|---|---|---|
| K1 | Medium (functional, not security) | `[aslan_pay]` mints a single-use token per render and stores it in a transient. Behind a full-page cache the same HTML (and token) is served to many visitors, so only the first click works; others get `token_expired`. Each uncached view also writes a transient. | Document "exclude pages with `[aslan_pay]` from page caching" in readme for 0.1.0; 0.2.0: mint the token on click via a nonce-protected REST call. |
| K2 | Low | Keys also live in the WC settings blob `woocommerce_aslan_settings` (autoload yes). Standard for every WC gateway; not rendered to the page after the fix. | 0.2.0: stop persisting keys in the blob (store only in `aslan_woo_*`). |
| K3 | Low | Webhook idempotency recorder is get-then-set on a transient (not atomic); concurrent duplicate deliveries could both pass. Order-state/marker guards make replays harmless. | 0.2.0: `add_option` based lock. |
| K4 | Low | Dev tools a major behind (phpstan 2, phpunit 13, phpcs 4). Not shipped. WPCS 3 pins phpcs 3. | Revisit with WPCS 4. |
| K5 | Low | `ShortcodePayRoute` has no unit tests (deferred to the Phase 15 E2E). | Add unit coverage in 0.2.0. |
| K6 | Info | Psalm runs WITHOUT `humanmade/psalm-plugin-wordpress`; it cannot resolve against `php-stubs/wordpress-stubs ^7.1` (every release needs `^5`/`^6`, or Psalm 4). WP stubs are loaded directly; WP escaping functions are not modeled as taint escapers (this can only add false positives, there were none). | Revisit when the plugin supports stubs 7. |
| K7 | Info | The Gateway form changes (masking, override validation) are unit-tested through `SettingsGuard` only; the WC integration suite and a live WC settings save were not run in this environment. | Run `npm run e2e` / integration suite before tagging. |

### Dependency pinning

- `aslan/payment-php 0.2.0` is pulled from the VCS repository (`Belkouche/aslan-payment-php-symfony`) and locked in `composer.lock` at commit `5ed7de3aaac7d068e46b962449738fe67011ef5b`.
- The release ZIP installs with `composer install --no-dev` from the lock file, so every build ships exactly that commit, not whatever `^0.2.0` resolves to later.
- Why this matters: the SDK is load-bearing. A silent minor upgrade can change HTTP behavior (retries, timeouts, error mapping) or validation rules and break production checkout. Upgrades are explicit: bump, re-run the unit and E2E suites, re-run this review.
- Transitive runtime deps (`symfony/http-client v8.1.11`, `symfony/contracts v3.8.1`, `psr/*`) are likewise lock-pinned.
- PHP is constrained to patched releases (`~8.2.35 || ~8.3.36 || ~8.4.27 || >=8.5.12`).

## Addendum — review of this review

A second pass at the review doc (same day) flagged four precision issues (rows 2, 10, 14, 19, 20 — fixed inline above) and five coverage gaps. Each gap is checked below and fixed in commit `security: review-of-review hardening` where a fix was warranted.

| # | Check | Status | Evidence |
|---|---|---|---|
| 26 | Webhook body size is bounded before HMAC. | ✅ (fixed) | Was unbounded (a 50 MB signed POST would be hashed and parsed before rejection). Now `WebhookRoute::MAX_BODY_BYTES = 65536`; oversize payloads return `413 payload_too_large` before HMAC, JSON-decode, or any DB write (`WebhookRoute.php:34-37`). Aslan webhook bodies are well under 64 KB. |
| 27 | Shortcode pay route rate-limiting. | ✅ (documented) | Route is nonce-protected (`ShortcodePayRoute.php:27-29`) and single-use-token-bound (`:38-48`), but a logged-in user with a valid `wp_rest` nonce can hit it as fast as they like, creating transient rows + Aslan API calls. v0.1.0 relies on: (1) `wp_rest` nonce lifetime (12-24h), (2) single-use `aslan_pay_*` transient deletion on first use, (3) Aslan API's own rate limits. Filed as K8 for 0.2.0 (per-IP throttle via `aslan_rl_ip_*` transient). |
| 28 | Diagnostic log content: what is actually recorded. | ✅ (fixed) | Audited every `DiagnosticLog::record()` caller. Call sites pass only event IDs and order/CPT IDs (`WebhookService.php:110,210`). No customer PII (email, name, phone), no card or BIN data, no secrets, no signatures. Hardening: `DiagnosticLog::MAX_MSG_LENGTH = 500` truncates any future caller that passes a longer string, which also bounds the `aslan_woo_log` option row size (100 rows × 500 bytes ≈ 50 KB worst case). |
| 29 | Admin settings-save nonce is scoped to the Aslan tab. | ✅ (fixed) | WC's own `woocommerce-settings` nonce is shared across every WC settings tab, so an admin's active nonce could be CSRF'd into saving the Aslan tab from a crafted form on any tab. Fixed by rendering a scoped nonce in `Gateway::admin_options()` (`aslan_woo_save_settings` action, `aslan_settings_nonce` field) and verifying it in an override of `Gateway::process_admin_options()` before calling the parent — on failure, `WC_Admin_Settings::add_error` surfaces a notice and the save short-circuits (parent returns before firing `woocommerce_update_options_payment_gateways_aslan`, so `persist_bridged_options()` is never called). Scoped nonce coverage is part of the K7 live-WC smoke test. |
| 30 | Uninstall removes all plugin data. | ✅ (fixed) | Was a gap: no `uninstall.php`, no uninstall hook — secret keys, webhook signing secrets, and the WC settings blob stayed in the DB after plugin deletion. Added `uninstall.php` at the plugin root (loaded by WordPress only on explicit delete, not on deactivation) which calls `delete_option()` for all 11 `aslan_woo_*` options plus the `woocommerce_aslan_settings` blob. Transients clean themselves up on TTL; no `$wpdb` DELETE on `wp_options` is attempted (unbounded on a shared table). |
